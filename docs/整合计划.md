# 长流整合计划（0.8）

> 目标：把已经塞进同一个 APK 的三套源码，整理成「一个内核 + 一套基础设施 + 三个场景」。
> 前提事实：三个 app 已合并，包名 `com.changliu.app`，唯一启动器 `ui.ChangliuShellActivity`。
> 本文件只做计划，不含代码改动。

---

## 0. 一句话

融合已经完成，但只是**把三份源码装进一个进程**，没有把重复的能力收成一份。
现在同一个能力平均有 2–3 份实现，各自读各自的配置，互不相通。

### 1.2 跨模块同名文件（重复实现的硬证据）

`Bank.kt` `Ledger.kt` `Lines.kt` `LinkProvider.kt` `Chat.kt` `Handoff.kt` `Intake.kt`

### 1.3 已经是好的部分（不要动）

- **唯一无障碍**：Manifest 只注册 `infra.a11y.ChangliuA11yService`。一手 `GateService`、总控 `GuardService` 虽然还挂着 `: AccessibilityService()`，但**没注册、不会运行**；它们的 `companion` 被 `ChangliuA11yService` 当状态桥调用（`markConnected` / `markForeground` / `markRunning`），所以不能直接删类。
- **唯一启动器**：`ui.ChangliuShellActivity`（唯一 LAUNCHER intent-filter）。
- **唯一 Application**：`ChangliuApp : YishouApp(), ZkHost`。
- **决策链已有分层**：`ZkGateLink` → `YsGateLink` → `Intercept`，顺序清晰，可直接复用为「一个 Gate + 三条策略」。

### 1.4 现在的乱在哪（按危害排序）

1. **配置不通**：驾驶员填的网关 key，一手和总控读不到；反过来也一样。用户在三个页面各填一次。
2. **拦截三份**：任何人改拦截规则都要改三处，且三处的草稿落盘、旋转恢复逻辑各写一遍。
3. **常驻服务重叠**：`KeepAliveService` 之外，一手 6 个前台服务 + 1 个磁贴服务（`ScrollTile`）仍在 Manifest 里（看屏、滚动、窗口、伴读、伴读语音、壁纸）。「唯一常驻」只在文档里成立。
4. **对话三套**：`app/GatewayBrain`、`yishou/assistant`+`partner`、`zongkong/core/agent/Chat.kt`，各自维护历史与 prompt，没有共享预算和限流。
5. **遗留的半死代码**，三类要分开处理，不能一刀切：
   - `GateService` / `GuardService`：不运行，但伴生对象仍在被调用；
   - `SelfHeal` / `Watchdog`：**不是死代码**，`Watchdog.noteWidget`、`SelfHeal.check` 都有真实调用点；`SelfHeal.kt` 里还额外声明了**第二个 `KeepAliveService` 类**（zk 包，未注册），与 app 的唯一常驻重名，最容易误读；
   - `.WatchdogJob`：是活的，`ChangliuApp` 和 `MainActivity` 都调 `schedule`。

## 2. 目标形态

```
:core            纯 Kotlin 逻辑（已有 17 个文件 / 1.9k 行，保持无 Android 依赖）
  ├─ 规则、状态机、长流引擎（Flow/Mood/Proactive/Memory/Tuning）
:infra           ← 新建。所有对外能力唯一实现
  ├─ llm        一个 ChatClient + 一套 LlmConfig + 一张服务商预设表
  ├─ speech     一个 Speaker（TTS）+ 一个 VoiceInput
  ├─ notify     一个 Notifier，渠道集中注册
  ├─ schedule   一个 Reminders，一个 Receiver，一个 BootReceiver
  └─ store      一套设置（单份 prefs）+ key 走 SecretBox
:scene:ys        一手业务：只留陪练/训练差异
:scene:zk        总控业务：只留工作/汇报差异
:scene:driver    驾驶员业务：只留拦截/自我察觉差异
:app             壳、无障碍、常驻、Gate
```

**判断标准**：一个类如果三个场景都用，就必须在 `:infra`；只为一场景存在，才留在 scene。

> 落地考量：`ys`/`zk` 现在是 library 模块，直接新建 `:infra` 会让 `ys`、`zk` 反向依赖它。
> 短期最省事的做法是**先把唯一实现放进 `:app` 的 `infra/` 包**，`ys`/`zk` 通过既有桥接拿；
> 等全部收完再抽成独立模块。这样每一步都能单独编译、单独回滚。

## 3. 分期

原则：**先清理、再统一、最后收敛 UI**。每期独立可编译、可回滚、可验收。

### P0 基线（必须最先做，约半天）

工程当前**没有 git 仓库**，任何大改都无法回滚。这一步不做，后面全是裸奔。

- `git init` + 首次提交（包含 `legacy/`、`patches/`、`dist/` 除外的大文件）
- 跑一次全量：`:core:test :ys:testDebugUnitTest :zk:testDebugUnitTest :app:assembleDebug`，记录 767 项基线
- 打 tag `v0.7.0-fusion` 作为「能用的版本」的锚点
- 模拟器装一次，录 5 条基准场景（启动、拦截、主动搭话、记忆消化、5 分钟静置）

验收：`git status` 干净；767 项 0 失败；tag 存在。

### P1 清理遗留与重名（不改行为，约 1 天）

**实测复核后，原计划的多数删除项被推翻**。下面每行的依据都来自实际引用扫描，不是猜测。

| 动作 | 对象 | 实测依据 |
|---|---|---|
| 暂不删，先抽状态 | `yishou/…/gate/GateService.kt` | 类体（392 行）确实没人 new、也没注册；但静态成员被一手 8 处真实调用：`GateActivity.hideCover()`、`PartnerService.bringToFront()`、`PartnerSessions.foreground`、`ScrollService.foreground`、`WindowViewModel.mayPullFrom()/bringToFront()`、两个页面读 `connected`/`problem`。要删必须先整类重写成工具对象。 |
| 暂不删 | `zongkong/…/guard/GuardService.kt` | `GuardService.running` 仍被 `Watch.kt:162`、`Watchdog.kt:181` 真实读取，不是死字段。 |
| **不能删** | `yishou/…/gate/GateTrace.kt` | 一手自己的 `GateDoctorScreen.kt` 在用（`init`/`recent`/`export`/`clear`/`stamp`）。原计划误判为重复副本。 |
| 可删，但要连带 | `yishou/…/gate/GateCover.kt` | 只被死的 `GateService` 使用；删它必须同时处理 `GateService`，否则编译不过。 |
| 保留 | `zongkong/…/system/SelfHeal.kt`、`Watchdog.kt` | `Watchdog.noteWidget`（PetWidget）、`SelfHeal.check`（zk 60s 循环）都在真实调用；`SelfHeal.kt` 里那个未注册的 `class KeepAliveService` 是重名隐患，但删它收益低、风险高。 |
| **不要动** | `.WatchdogJob` | `ChangliuApp`、`MainActivity` 都调 `WatchdogJob.schedule`，是活的。 |

**结论**：P1 原定的「删死代码」收益远小于风险，降级为「只加注释说明为什么留着」。
真正的重复（LLM / 配置 / 通知 / TTS）在 P2 处理，那里才有净收益。

验收：767 项测试仍全绿；APK 体积不增；拦截场景无回归。

### P2 统一 API 层（收益最高、风险可控，约 2–3 天）

按「对外能力」逐个收成一份，**旧的类保留签名、内部转调新实现**，避免一次改几百处调用点。

1. **LLM**：`app/infra/llm/ChatClient.kt` 为唯一实现（它已是一手版的超集）。`yishou/llm/ChatClient`、`zongkong/core/Llm.kt` 改为薄委托。
2. **配置**：一套 `LlmConfig` + 一张服务商预设表（把一手 8 个 + 总控 9 个去重合并）+ 一份存储，key 统一走 `SecretBox`。
   - 兼容：首次启动时把旧的三处配置读一次，迁移进新存储，旧 key 保留不删。
3. **TTS**：一个 `Speaker`，app 内 3 处直接 `new TextToSpeech` 改为调用它。
4. **通知**：一个 `Notifier`，所有渠道集中注册，渠道 id 保持不变（避免用户已设置的静音被重置）。
5. **提醒/闹钟**：一套 `Reminders` + 一个 `ReminderReceiver`，保留旧 action 名的兼容分支。

验收：三个页面填的 key 互相可见（唯一真相）；767 测试绿；模拟器验证 TTS、通知、提醒各一次。

### P3 统一入口能力（控机 + 对话，约 3–4 天）

1. **拦截**：只留 `app/.infra.gate.GateActivity`（已支持 `MODE_GATE/BLOCK/HQ`）。删一手、总控两份页面，其跳转改走唯一入口。三条策略保持现有顺序。
2. **对话**：只留一套会话与历史存储，三场景各自提供 system prompt 与工具白名单；统一 token 预算与限流（现在三套各算各的）。
3. **MainActivity**：确认一手/总控首页是否仍需独立入口；若壳已覆盖，改为壳内跳转，不保留独立 Activity。

验收：拦截三种模式各跑一次；对话在三场景各跑一轮并确认历史互通；767 测试绿。

### P4 存储与 UI 收敛（可选，收益最大、风险最高，5 天+）

- 一手 Room（33 个 `@Entity`）是否并入单库
- 设置页三份合一
- 壳内三场景页面去重

**建议缓做**：Room 合并要写迁移链，风险与收益不成比例。先把 P2/P3 做完再看。

## 4. 手法：薄适配层，不做大爆炸重写

每个被收编的旧类改成这样，调用点零改动：

```kotlin
// 旧签名保留，内部转调唯一实现
@Deprecated("统一到 infra.llm.ChatClient")
class ChatClient(private val delegate: com.changliu.app.infra.llm.ChatClient = App.chat) {
    suspend fun complete(system: String, user: String, kind: String = "其他", json: Boolean? = null) =
        delegate.complete(system, user, kind, json)
}
```

好处：每收一个能力就能立刻编译、立刻测、立刻回滚；不会出现改到一半整个工程红掉。

| 风险 | 处理 |

## 8. 执行记录（P2 已落地，2026-11-07）

计划与实做的差异都记在这里，免得后人对着上面的计划猜现状。

### P2-1 姿态改了：从「放进 :app」改成「独立 :infra 模块」

计划里写的是「先把唯一实现放进 `:app` 的 `infra/` 包」。实做时发现行不通：
`:ys`、`:zk` 是 library 且被 `:app` 依赖，它们**不能反向依赖 app**，放 app 里 ys/zk 就引用不到。
所以新建了 `:infra`（`com.android.library`，namespace `com.changliu.infra`，minSdk 26、jvmTarget 17），
`app` / `ys` / `zk` 三方都 `implementation(project(":infra"))`。

### P2-2 手法改了：typealias 薄壳走不通，改成改导入

计划第 4 节设想的「旧类保留签名、内部转调」在一手这边**证伪**了：
Kotlin 不支持经 typealias 访问嵌套类，`LlmResult.Ok` / `LlmResult.Err` 全部解析失败
（报错 `Unresolved reference 'Ok'` 与 `'when' expression must be exhaustive`）。

最终做法是直接的：把一手 58 个文件里对 6 个符号（`ChatClient` / `LlmConfig` / `LlmError` /
`LlmResult` / `SseParser` / `UsageSink`）的引用改指 `com.changliu.infra.llm`，删掉一手那两份实现。
`com.yishou.app.llm` 包里剩下 12 个文件是一手自己的业务代码（`BankTidy` / `CardGen` / `Coach` /
`DrillGen` / `Vision` 等），**不是重复品，留在原处**，只是补了一条 `import com.changliu.infra.llm.*`。

### P2-3 总控也接完了

`zongkong/core/Llm.kt` 从 90 行降到 62 行：HTTP 请求体整段删掉，改成把 `AiConfig` 翻成 `LlmConfig`、
把 `LlmResult` 翻回 `ApiResult`。为保持行为不变，`temperature = 0.2` 和总控自己的
「还没有配置 AI 接口（设置 → AI 接口）」文案都显式保留。
顺带把 `LlmError.httpMessage` 从 private 提成公开，让总控的对话通路复用同一份状态码措辞表，不再各写一份。

### 总控里那个同名 ChatClient 不是重复，别删

`zongkong/core/agent/Chat.kt:64` 也有一个 `class ChatClient`，但它做的是**带工具调用的对话**
（`tools` / `tool_calls` / 多模态 `image_url` / `ChatMsg` 序列化），:infra 的 ChatClient 只做
纯文本与单轮识图，没有 tools 协议。把它并进 :infra 等于给 :infra 新增一套工具调用能力，
超出「收掉重复 HTTP 客户端」的范围，**保留**。

1. **`unitTests.isReturnDefaultValues = true` 让 org.json 变成桩**：总控接完 :infra 后

### P2-4 密钥统一走 SecretBox（2026-11-07 补做）

计划第 2 条里「key 统一走 SecretBox」这一句，实做时发现是**一个真实的安全缺陷**而不只是重复：

| 端 | 原来怎么存 key | 结论 |
|---|---|---|
| 驾驶员 | `SecretBox`（AndroidKeyStore AES/GCM，盘上只有密文 + IV） | 已合格 |
| 一手 | `EncryptedSharedPreferences` + `MasterKeys`（打开失败只删重建，明确不退回明文） | 已合格 |
| 总控 | `config.json` 里**明文** `ZkJson.encodeToString(Config.serializer(), c)` | 最弱一环，缺陷 |

融合成一个 APK 后，三端密钥落在同一个 `filesDir` 下，最弱的一环决定全部。改动：
